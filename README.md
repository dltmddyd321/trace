# 따라찍 (Trace)

구도를 고르면 카메라에 겹쳐 보여주고, 사용자는 따라 맞추기만 하면 되는 안드로이드 앱입니다.

https://github.com/dltmddyd321/trace/raw/main/docs/demo.mp4

> 재생되지 않으면 [docs/demo.mp4](docs/demo.mp4) 에서 보실 수 있습니다.

## 설치

[**Releases 에서 APK 내려받기**](https://github.com/dltmddyd321/trace/releases/latest) · Android 10(API 29) 이상, arm64

배포용 APK 에는 **API 키가 들어있지 않습니다.** 키를 APK 에 넣으면 받은 사람이 꺼내 쓸 수 있기 때문입니다.
그래서 `사진에서 따오기`는 바로 동작하고, `배경 찍고 추천받기`는 안내만 뜹니다.
AI 추천까지 쓰려면 아래 실행 절차대로 직접 빌드해야 합니다.

## 왜 만들었나

사진 찍는 걸 유난히 어려워하는 친구가 있습니다. 같이 여행을 가기로 했는데, 이 친구는 매번
"어떻게 서 있어야 해?"보다 "내가 찍으면 이상하게 나온다"를 먼저 걱정했습니다. 실제로 찍어보면
카메라도 좋고 장소도 좋은데 결과가 아쉬웠습니다.

옆에서 보니 문제가 분명했습니다. **구도를 모르는 게 아니라, 아는 걸 지금 이 화면에 적용하지
못하는 것**이었습니다. "삼분할로 찍어"라고 말해줘도 눈앞의 카페에서 어디에 세워야 하는지는
별개의 문제입니다.

그래서 여행 전에 만들었습니다. 말로 설명하는 대신 **화면에 겹쳐서 보여주면** 되지 않을까 싶었습니다.

## 무엇을 푸는가

카메라 성능이나 보정의 문제가 아니라 **구도와 비율을 모르기 때문**입니다. 같은 장소, 같은
사람, 같은 폰으로 찍어도 누가 찍느냐에 따라 결과가 갈립니다.

찍는 사람이 막히는 지점은 셋입니다.

- 인물을 프레임 어디에 둘지 모릅니다 — 습관적으로 한가운데 놓습니다
- 얼마나 크게 담을지 모릅니다 — 전신인지 반신인지, 머리 위 여백을 얼마나 줄지
- 배경의 선을 어떻게 쓸지 모릅니다 — 테이블 모서리, 창틀이 구도를 지탱한다는 감각이 없습니다

마음에 드는 사진을 보고 "이렇게 찍고 싶다"고 생각해도, 막상 카메라를 들면 그 사진이 어땠는지
떠오르지 않습니다. 사진첩을 다시 열어 확인하고 다시 카메라로 돌아오고, 그 사이에 기억은 흐려집니다.

이 앱은 **그 사진의 자세와 배치를 본떠 촬영 화면에 겹쳐둡니다.** 사용자는 판단하거나 기억하지
않고 따라 맞추기만 하면 됩니다. 몇 번 따라 찍다 보면 감이 붙는다는 게 원래 의도입니다.

## 두 가지 진입 경로

```
홈 ─┬─ 배경 찍고 추천받기 → 배경 촬영 → 자연어 요청 → AI 제안 2~3안 ─┐
    └─ 사진에서 따오기 → 갤러리 사진 선택 → 온디바이스 추출 ─────────┴─ 카메라(오버레이) → 무음 촬영
```

**경로 A — 사진에서 본뜨기.** 마음에 드는 인물 사진을 고르면 그 자리에서 실루엣과 자세 라인을
추출해 템플릿으로 씁니다. MediaPipe 가 기기 안에서 처리하므로 사진은 앱 밖으로 나가지 않습니다.

**경로 B — 배경에서 제안받기.** 눈앞의 배경을 찍으면 AI가 그 자리에 맞는 구도를 제안합니다.
"창가에 앉은 모습으로" 같은 요청을 덧붙일 수 있습니다.

경로가 달라도 산출물은 같은 형태의 템플릿이고, **카메라에 그리는 코드는 하나입니다.**

## 설계에서 내린 판단

### 저작권을 우회가 아니라 설계로 풀었다

레퍼런스 사진을 앱에 담으면 저작권 문제가 생깁니다. 흔한 대응은 출처를 표시하거나 라이선스가
허용되는 사진만 쓰는 것입니다.

여기서는 **배포되는 데이터에서 이미지를 없앴습니다.** 템플릿 하나는 정규화된 좌표 몇십 개와
윤곽 패스가 전부고 원본 이미지는 APK에 들어가지 않습니다. 구도·비율은 아이디어라 저작권
보호 대상이 아니므로, 좌표만 추출해 쓰는 것은 사실 데이터 추출에 해당합니다.

부수 효과로 런타임에 ML 의존성이 사라지고 APK가 가벼워졌습니다.

### 미리 만든 템플릿만으로는 부족했다

처음엔 경로 A만 만들려 했습니다. 그런데 템플릿을 20개 만들어도 사용자가 실제 서 있는 장소와
맞을 확률이 낮습니다. 카페 창가 템플릿을 골랐는데 눈앞의 카페는 창이 반대편이면 쓸 수 없습니다.

경로 B는 눈앞의 장면에 대한 답을 줍니다. 문제 정의가 "이 상황에서 어떻게 찍어야 할지
모른다"였으므로 여기에 더 직접 답합니다.

### 샷 유형을 먼저 정하지 않으면 깨진다

배치를 "어디에 놓을까" 하나로 보고 구현했다가 실패했습니다. 의자와 테이블로 꽉 찬 카페 배경에
전신을 넣으니 **다리가 테이블을 관통했습니다.** 설 바닥이 없는데 세운 것입니다.

그래서 판정을 3단계로 나눴습니다.

1. **샷 유형** — 빈 바닥이 있는가, 앉을 자리가 있는가, 둘 다 없으면 전경 크롭
2. **위치와 크기** — 시각적 무게의 반대편, 배경을 덮지 않게, 시선 방향에 여백
3. **크롭** — 어디서 자를지

1단계가 성패를 가릅니다. 이 절차는 `tools/prompt.md`와 앱의 시스템 프롬프트에 같은 내용으로 들어있습니다.

### 인물이 프레임에 다 들어갈 필요가 없다

배치 모델에 "실루엣이 프레임 안에 전부 들어가야 한다"는 가정이 숨어 있었습니다. 무릎 아래가
잘린 사진이 오히려 구도가 좋은 경우가 많은데도.

`box`가 0~1을 벗어날 수 있게 하자 두 가지가 한꺼번에 풀렸습니다.

- **설 바닥이 없는 배경도 성립합니다** — 발이 안 보이면 바닥도 필요 없습니다
- **포즈 라이브러리가 작아도 됩니다** — 전신 자세 하나로 전신·무릎위·허리위를 다 커버합니다

`crop`은 라벨이 아니라 **실제로 실루엣을 잘라냅니다.** 라운지 자세의 뻗은 다리로도 테이블 앞
허리 컷을 만들 수 있는 게 이 덕분입니다. 자르는 높이는 비율이 아니라 관절 위치에서 계산합니다 —
자세마다 허리·무릎 높이가 달라 비율로 맞추면 어떤 자세는 허벅지를, 어떤 자세는 배를 자릅니다.

### 목록과 카메라가 같은 렌더러를 쓴다

섬네일 이미지를 따로 만들지 않고 `PoseOverlay` 하나를 두 화면이 공유합니다. 명세가 하나라
고른 구도와 카메라에 뜨는 구도가 **구조적으로 어긋날 수 없고** 섬네일 에셋을 관리할 필요도 없습니다.

### 추출은 기기 안에서 한다

경로 A 는 사진을 서버로 보내지 않습니다. MediaPipe 가 기기에서 처리하고 남는 것도 좌표뿐이라
원본이 저장되지도 전송되지도 않습니다. 남의 사진을 다루는 기능에서 이 경계가 중요하다고 봤습니다.

### 무음 촬영은 촬영 경로를 피해야 가능하다

한국·일본 출시 단말은 카메라 HAL이나 프레임워크에서 셔터음을 강제 재생하고 **앱이 끌 수 있는
API가 없습니다.** `ImageCapture` 대신 프리뷰 스트림에서 프레임을 뽑아 저장하는 이유입니다.
셔터를 누르지 않으니 단말이 소리를 낼 계기 자체가 없습니다.

**국내 출시 갤럭시 S24(SM-S921N, Android 16)에서 실제로 확인했습니다.** 벨소리를 켠 상태에서
기본 카메라는 셔터음이 나고 이 앱은 나지 않습니다. 셔터음을 강제하는 바로 그 기기라 검증 대상으로
적합했습니다.

해상도를 내주는 대신, 회전을 직접 처리하게 되면서 저장 방향이 가로로 눕던 문제도 같이 해결됐습니다.

### minSdk 29

`WRITE_EXTERNAL_STORAGE`가 불필요해지는 경계가 정확히 29(scoped storage)입니다. 28 이하를
지원하는 순간 권한 분기를 따로 짜야 합니다. 앱이 요구하는 권한은 **카메라 하나뿐**입니다.

## 실행

경로 B(AI 추천)를 쓰려면 Gemini API 키가 필요합니다. [Google AI Studio](https://aistudio.google.com/apikey)
에서 무료로 발급받아 `local.properties`에 추가합니다.

```properties
geminiApiKey=AIza...
```

키가 없어도 빌드되고 경로 A는 정상 동작합니다. 해당 기능만 비활성화됩니다.

```bash
./gradlew assembleDebug
```

### 포즈 자산 추가

```bash
cd tools
python3.12 -m venv .venv
./.venv/bin/pip install mediapipe==0.10.35 opencv-python numpy
curl -sL -o models/pose_landmarker_heavy.task \
  https://storage.googleapis.com/mediapipe-models/pose_landmarker/pose_landmarker_heavy/float16/latest/pose_landmarker_heavy.task

./.venv/bin/python extract.py refs/photo.jpg   # → out/photo.json + out/photo_check.png
```

`_check.png`로 추출 결과를 눈으로 확인한 뒤 `app/src/main/assets/poses/`로 복사합니다.

> MediaPipe는 **0.10.35로 고정**합니다. 1.0.x는 macOS에서 Metal 초기화에 실패해 프로세스가
> 죽고, CPU 델리게이트를 지정해도 그래프 내부에서 터져 우회할 방법이 없습니다.

## 개발 중 막혔던 것

| 문제 | 원인과 해결 |
| --- | --- |
| MediaPipe 1.0이 프로세스째 죽음 | macOS Metal 초기화 실패. 0.10.35로 고정 |
| 검색으로 모은 사진이 못 쓸 수준 | 장면(`woman sitting cafe window`)이 아니라 장르(`full body portrait`)로 검색해야 인물 사진이 나옵니다 |
| 얼굴에 점이 찍혀 지저분함 | 랜드마크 0~10 제외. 눈·코·입 위치는 구도에 쓸모가 없습니다 |
| 다리가 테이블을 관통 | 샷 유형 판정 누락 + crop 미구현 |
| 목록 섬네일의 구조선이 인물과 어긋남 | 인물만 확대하는 모드와 원본 구도를 보여주는 모드를 분리 |
| 저장 사진이 가로로 누움 | 센서 회전을 직접 적용 |
| 사진 선택 시 앱이 죽음 | `Canvas: trying to draw too large(199756800bytes)`. 원본을 축소 없이 그렸습니다. 디코딩 단계에서 1600px로 제한 |
| 온디바이스 추출이 사람을 못 찾음 | 세그멘테이션 마스크는 픽셀당 float 신뢰도인데 ALPHA_8 이미지로 읽었습니다. float 버퍼로 직접 읽도록 수정 |
| 16KB 페이지 정렬 경고 | MediaPipe 0.10.21 의 네이티브 라이브러리. 0.10.35 로 올리고 APK 의 ELF 헤더를 직접 읽어 확인 |
| AI 제안대로 놓으니 인물이 너무 작음 | 자산의 가로세로비를 모르니 선 자세 기준의 좁은 박스를 내놓습니다. 앉은 자세는 가로로 넓어 비율 유지 과정에서 통째로 줄어듭니다. 비율을 프롬프트에 넣어 해결 |

각 단계는 **검증 스크립트로 눈으로 확인하며** 진행했습니다. 추출한 좌표를 원본 위에 다시 그려
보는 장치를 1일차에 먼저 만든 덕분에, 위 문제 대부분을 자산을 여러 개 만들기 전에 잡았습니다.
